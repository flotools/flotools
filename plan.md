# Flo Tools: architecture

This is the agreed design of the native app, described as the code has it now. It began as the merge of two plans, by Fable (`.pi/jobs/plan-fable/response1.md`) and Codex (`.pi/jobs/plan-codex/response1.md`), followed by a native redesign that both reviewed (`.pi/jobs/native-design-codex/response1.md`, `.pi/jobs/native-design-fable/response1.md`) and the owner decided on 2026-11-03 (journal J-89). The port and the redesign are finished. Their step-by-step sequence and the diagnosis of the first two-macro proof are in git history (this file before 2026-11-03's rewrite) and in the journal.

## 1. Goal and fixed rules

Flo Tools is a menu bar app that makes Pro Tools usable with VoiceOver by driving it through the Accessibility API. It replaces the Keyboard Maestro (KM) macro library, which is retired. The KM export in `reference/` is a frozen record of how each macro was ported (`reference/macros/INDEX.md`, "Ported" column).

The rules in `AGENTS.md` ("Rules that must not change") apply: hotkeys and windows are kept unless changed on purpose (section 9) and are pinned by `KeymapTests`; Apple events only for VoiceOver; the Accessibility API for everything in Pro Tools; spoken text as in the JXA unless a reason is stated; macOS 13; Swift 6 strict concurrency; Sparkle for updates. Flo Mouse is out of scope and moves to a separate project (owner decision, 2026-11-02).

## 2. Targets and dependency direction

| Target | Owns | Depends on |
|---|---|---|
| `FloSystem` | Generic macOS infrastructure: `AXElement` and `AccessibilityActor`, `VoiceOver` and `VoiceOverActor`, `HotKeyCenter`, `KeyCombo` and the one key-name table, `Keyboard`, `Mouse`, `FrontWindowObserver`, `WorkspaceEvents`, `Sound`, `SystemSpeech`, Flo Tools' own windows (`Chooser`, `TextWindow`), `FloError`, `Log` | Apple frameworks |
| `FloProTools` | Pro Tools knowledge: `ProToolsApp`, `ProToolsWindowKind`, `MixWindow`, `TrackStrip`, `TrackList`, `EditWindowControl`, `ProToolsSetting`, `PlugInWindow`, `FadeDialog`, the front window facts and `AnnouncementGuard`, `ProToolsUpdate` (waiting for Pro Tools to show a change) | `FloSystem` |
| `FloEngine` | The command model and runtime: `Command`, `CommandID`, `Trigger`, `Scope`, `Mode`, `ModeCondition`, `CommandRun`, `Engine`, `DoublePressDecider`, `Watches`, `SpokenError`, `FrontContext`, `Preferences` and `PreferencesStore` | `FloSystem`, `FloProTools` |
| `FloFeatures` | The commands, one folder per feature; `FloFeatures.all`, `SessionState`, `Lifecycle`, the plug-in view installer | `FloSystem`, `FloEngine`, `FloProTools` |
| `FloTools` | The app: `AppDelegate`, status menu, permission prompts, the preferences panel, the diagnostic log header | all of the above |

Nothing below `FloFeatures` knows a command by name. `FloEngine` imports `FloProTools` because a scope names Pro Tools window kinds; a protocol in the engine with one Pro Tools implementation would only add a layer, and Flo Tools drives only Pro Tools. There are no protocols for mocking: dependencies are concrete instances passed through initializers or captured by closures. The only shared instances are the two global actors, which Swift requires to have one.

## 3. Command model

- A `Command` has an ID (`CommandID`, such as `inspector.speakToggleSolo`, kept from the KM group and macro), a name, a summary for `COMMANDS.md`, a scope, a mode condition, triggers and an action. Feature files declare their commands, and `FloFeatures.all` lists them. "Macro" is used only for Keyboard Maestro artifacts, and KM UIDs appear only in `reference/`.
- Triggers are `.key("Ctrl+2")`, a hotkey with its phase (pressed or released) parsed by `KeyCombo(literal:)`, and `.statusMenu`. KM's focused-window and application triggers belonged to macros that `Lifecycle` and the window observer absorbed, so the engine has none.
- A `Scope` is any Pro Tools window or a set of `ProToolsWindowKind`s. Each front window title has exactly one kind, from one classification function in `FloProTools`: Mix, Edit, Plug-in, AudioSuite, Fade In, Fade Out, Crossfade, Batch Fades, setup tabs, Keyboard Shortcuts, other. The order of checks lives only there; a title starting with "Plug-in:" is a plug-in window even if it also contains "Audio Suite:". With one kind per window, ties can be proved absent.
- `Mode` is app state the keymap reads, so far only the Inspector, on or off. The temporary Inspector is a hold that turns it on and, on release, always off. Track view keys apply while the Inspector is off, so no command enables or disables another to swap keys.
- The engine indexes commands by key. A command for specific window kinds beats an any-window command. Two commands for the same key, phase, window kind and mode are an error at install and in the tests, instead of depending on declaration order; a duplicate ID is too. `Binding` and `Keymap` are not types of their own, because every command's keys share one scope and mode condition. A separate binding would be worth it only once one command needs different windows or modes per key.
- While Pro Tools is in front but its window title is not read yet (about 35 ms after activation, J-105), a key that some window kind gives to a command of its own is not taken, so its any-window command cannot run in the wrong window; it goes on to Pro Tools like the other window-only keys (Codex context-gap review, 2026-11-03; today only Shift+Up and Shift+Down, which Batch Fades overrides). Keys pressed in that gap are not held back and routed later: replaying them would reorder them against keys Pro Tools gets directly, break double-press timing and lose hold durations, and would need an event tap that buffers the whole keyboard stream.
- An action is a body, a single and double pair, or a hold with press and release. Bodies are `@Sendable (CommandRun) async throws -> Void` and nonisolated (owner, 2026-11-02): Pro Tools reads run on `AccessibilityActor`, speech on `VoiceOverActor`, and engine state on the main actor, so no body blocks hotkeys or the menu. `CommandRun` carries the command, its origin (hotkey, run by the app, or an event), the front context and the engine. Its invocation ID for the log is `Log.invocation`, which the tasks it starts inherit.
- The engine owns double press, keyed by `CommandID`, through the pure `DoublePressDecider`, tested with explicit instants. A command chooses whether the done sound (Tink in the JXA) plays before or after its double action, or not at all. Repeat events are not taps. Pending singles carry a generation number and are voided on disable, context change, timeout change and stop.
- Commands run through one serial queue, so two cannot interleave across `await`. A queued hotkey or event run checks when it starts that Flo Tools and the command are still enabled, that its scope still applies, that the front app is the process it was accepted for and, for a command scoped to some windows, that the same window is in front; otherwise it is dropped and logged. Of the mode, only the Inspector turning on is checked, because the keys of an Inspector-off command then pan; a single press of S accepted while the temporary Inspector key was held still speaks after the release. The temporary Inspector hold is recorded when the key event arrives and cleared on release, focus loss, disable and stop, outside the queue.
- `Watches` holds one task per watch, such as the level meter, the plug-in monitor and the MIDI event column, outside the queue. They poll every 100 ms, because Pro Tools sends no Accessibility notification for many value changes (checked live for preset changes). The plug-in monitor finds its sliders again on each poll; keeping them was measured (J-176) and rejected, because the gain was small and a stale element would read a closed window. Two watches keep an element for a bounded time: the meter watch keeps the strip while the name under the VoiceOver cursor stays the same, and the MIDI event watch keeps its field for `readsPerLookup` reads (one second) and finds it again after a failed read. `engine.cancelAll()` stops the queue and the watches, like KM's Cancel Macros.
- Shared behavior is a shared Swift function, not one command running another. Command families share one parameterized implementation: send and insert slots, fade dialogs, counters, track lists, plug-in navigation and passed-on shortcuts. Sends and inserts keep separate layout rules, because their Accessibility layouts differ.
- Enable state keeps apart the user's "Flo Tools Enabled" switch (persisted by `PreferencesStore`), the Inspector mode, and suspension reasons: VoiceOver not running, and the Pro Tools Keyboard Shortcuts window open, kept while that window exists behind another, as in KM. Removing one reason does not clear another or override the user's choice. Suspensions are not persisted. Whether Toggle Temporary Inspector works is derived from the preferences, not a user choice.

## 4. System layer

- Accessibility: `AXElement` is isolated to the global `AccessibilityActor`, so a busy Pro Tools blocks that actor and not the main actor. It has typed attributes, role-filtered child lists and lookups in the JXA vocabulary (`groups`, `button(_:)`). Immediate-child lookups never fall back to a whole-tree search. The global messaging timeout is 1 s. A press that may open a pop-up menu uses 0.25 s on that element, because Pro Tools answers it only when the menu closes, and counts a timeout as done when a menu window is then on screen.
- Reads: only "no value" and "no such attribute" are absence; any other `AXError`, such as a busy app or a closed window, throws. A failed read is never treated as "off". A lookup a command cannot continue without goes through `AXElement.required`, which throws `FloError.notFound` and, while the log is on, logs a bounded dump of where the lookup stopped. Actions throw with the `AXError`.
- One error model: `FloSystem` defines `FloError`, with cases for Accessibility failures, VoiceOver failures, timeouts, missing elements and actions that could not be done. `FloProTools` throws it with Pro Tools descriptions, such as a missing window or no track under the cursor. What the user hears is decided in one table in the engine, `SpokenError`. Cancellation is silent. A failure to speak an error is logged, never retried by speaking.
- VoiceOver: `say` and the cursor reads send VoiceOver's Apple events directly (`NSAppleEventDescriptor`, no AppleScript source), with the text as a parameter and a 2 s timeout per call, about 3 ms per call instead of about 30 ms for compiled AppleScript (measured 2026-11-02). They run on `VoiceOverActor` (section 8). The one warning VoiceOver cannot speak, that it does not take Flo Tools' Apple events, goes through `SystemSpeech`.
- Hotkeys and synthetic keys: Carbon `RegisterEventHotKey`, registered for the current context, with press and release events. Passing a key on and sending keystrokes post to Pro Tools' process with `CGEvent.postToPid`, through one serial queue, with a 10 ms hold because Pro Tools ignores a key down followed at once by its key up. Every synthetic event carries `Keyboard.syntheticMarker`.
- Mouse: events go to the window under the pointer, so they are posted to the whole system. Each operation names the app it is for and posts nothing when another app has come to front meanwhile, for example while the command was speaking. The check narrows the race rather than closing it.
- Context: `FrontWindowObserver` attaches Accessibility notifications (focused window changed, title changed, menu closed) to the front app and polls only while not all of them are registered, retrying on every read. Reads run on `AccessibilityActor`; the front app's process is published at once with an unknown title, and a read's result is dropped if a change was reported while it ran (`WindowTitleReads`, tested without Accessibility). `FrontContext` carries the process, the window number, the title and the window kind. `WorkspaceEvents` reports app launch and quit and VoiceOver on and off.
- Logger: one `Log`, specified in `AGENTS.md` ("Diagnostic log"). Warnings and errors in the unified log are marked private, because they can carry track names, which the owner approved only for the opt-in file.

## 5. Pro Tools layer

`FloProTools` is the one place where Accessibility paths become named things: `ProToolsApp.running()`, its windows (`mixWindow()`, `trackWindow(_:)`, `plugInWindow(_:)`, fade dialogs), `TrackStrip` with name, kind, solo, mute, record arm, sends, inserts, volume, pan, meters and comments, `TrackList`, Edit window controls such as counters, grid and nudge, settings in menus and toolbars, and `keystroke(_:)`. Reads return small value types, so the next step is a pure function that unit tests can cover.

Unsolo All Tracks is the model for multi-step changes: check the window and process, read the eligible tracks (not master, safe or inactive), suspend the groups and confirm it in the Group List, process ordinary tracks before folders, check each track again before clicking, resume the groups on completion, error or cancellation, and announce success only after full success. Partial completion is reported as such.

## 6. Preferences, lifecycle and state

- Preferences live in UserDefaults (`com.chikim.FloTools`), read once by `PreferencesStore` at launch and passed down; the preferences panel is the only writer. The KM `flotools.json` is neither read nor migrated (owner, 2026-11-02). Missing values are defaults; a timeout outside 200, 300, 400 and 500 ms (only possible with `defaults write`) is logged and replaced by 200. Tests use a throwaway suite that they delete.
- `FloFeatures.apply(_:to:)` is the one home of KM's Refresh Preference (double-press timeout, temporary Inspector), and `InspectorMode.applyStartState` sets the Inspector from "starts with Flo Tools inspector". The menu item "Preferences…" and the Flo Tools Preferences command (Ctrl+Cmd+,) open the same panel.
- `Lifecycle` replaces KM's Global group, because those macros change Flo Tools itself and must work while it is suspended: suspending while VoiceOver is off or the Keyboard Shortcuts window is open, `cancelAll()` on Pro Tools quit, stopping the meter watches on a window change, and on Pro Tools launch checking that VoiceOver takes Apple events, resetting session state and applying the preferences and start state. A plug-in window coming to front, or changing its title to another plug-in, loads that plug-in's default view.
- Transient KM variables became typed state in `SessionState`, owned by the feature that uses it and reset at the matching boundary (Pro Tools quit, window change). A clip mark records its Edit window and is dropped when that window is gone.
- Updates: `Updater` in the app target wraps Sparkle's standard controller and builds the Updates submenu: the version as a dimmed label, Check for Updates, and four settings. Automatically Check and Automatically Download are Sparkle's own settings, which it keeps in UserDefaults. Automatically Install (install a background download now and relaunch, not on quit) and Include Beta (allow the appcast's `beta` channel) are `PreferencesStore` keys. A setting that depends on one that is off is dimmed. Flo Tools has no Dock icon, so Sparkle shows a scheduled update's window behind the front app; VoiceOver says that an update is available instead. The feed is `https://flotools.org/flotools/appcast.xml` (`appcast.xml` on `gh-pages`), signed with the EdDSA key in the owner's keychain, whose public half is `SUPublicEDKey`. A release adds one `<item>`: set `CFBundleShortVersionString` and raise `CFBundleVersion` by one in `Info.plist`, build with `FLO_SIGN_IDENTITY="Developer ID Application: …" scripts/build-app.sh` (a Developer ID identity also gets a secure timestamp), submit a `ditto` zip with `xcrun notarytool submit --keychain-profile "FloTools Installer-notary" --wait`, staple the app, zip with `ditto -c -k --keepParent`, upload the zip to a GitHub release, run `.build/artifacts/sparkle/Sparkle/bin/sign_update` on it for `sparkle:edSignature` and `length`, and add `sparkle:version` (the build number), `sparkle:shortVersionString`, `sparkle:minimumSystemVersion` 13.0 and, for a beta, `<sparkle:channel>beta</sparkle:channel>`. Tag the release `v` plus the shown version, and mark a beta as a GitHub pre-release.
- Plug-in view files keep the KM format (JSON in `.txt`) and location, `~/Library/Application Support/Flo Tools/Plug-In Views/`. Filenames from window titles are sanitized to one path component. The app copies the views it ships there on first launch, without overwriting the user's files. Views added in a later version do not reach users who already have them installed; a Sparkle update does not change this.

## 7. Tests and tooling

- Unit tests are deterministic, with no sleeps for synchronization. They cover routing and precedence, the tie check, enable and suspension state, double-press decisions, the queue and cancellation, error wording, preferences, window classification, title read ordering, the log file, and per-feature text and parsing.
- `KeymapTests` pins every binding and the routing of shared keys in `Tests/Baselines/Keymap.txt` and `Routing.txt`. `CommandReferenceTests` generates `COMMANDS.md` and fails when it is out of date. Both regenerate with `FLO_WRITE_BASELINES=1`.
- `scripts/build-app.sh` fails when no signing identity is found instead of falling back to ad hoc; `FLO_SIGN_IDENTITY=-` asks for ad hoc explicitly.
- Live tests in Pro Tools follow `AGENTS.md`. `scripts/vo.sh` reads and moves the VoiceOver cursor through VoiceOver's AppleScript dictionary and invokes VoiceOver commands by name.

## 8. Decisions and their reasons

| Topic | Options | Decision |
|---|---|---|
| Key input | Carbon hotkeys with `postToPid` (Fable), or one `CGEventTap` (Codex) | Carbon with `postToPid`: the smaller change, it keeps the working path and needs no new permission. Carbon supports hotkeys without modifiers and release events. The backtick registration stays alive for the whole hold, and the hold is tracked apart from routing. The synthetic marker is for logs only; Carbon hotkey events do not carry it. Switch to an event tap only if a live check fails. A physical keyboard check is still open. |
| VoiceOver isolation | Main actor (Fable), or a separate helper executable (Codex) | A dedicated global actor, `VoiceOverActor` (2026-11-03, Codex infrastructure survey). A helper adds a second signed executable and IPC for a risk not yet seen, but the main actor was wrong too: each call waits up to its 2 s timeout, and an unresponsive VoiceOver then held up hotkey routing, the temporary Inspector release and the menu. Each caller awaits its calls, so its own speech stays in order; separate callers get no first-come order. Still to check live: VoiceOver unresponsive while keys are pressed. |
| Accessibility threading | Global actor (Fable), or a thread with its own run loop (Codex) | Global actor: simpler and enforced by the compiler. The messaging timeout bounds each call, not a whole traversal, so long jobs such as Unsolo All check for cancellation between operations. Observers keep an explicit run-loop owner. |
| Command body isolation | Nonisolated bodies, or main-actor bodies | Nonisolated (owner, 2026-11-02). A main-actor body would block hotkeys, the menu and the temporary Inspector release whenever Pro Tools is slow; the cost is an `await` on each Pro Tools read. |
| Targets | Four libraries (Fable), or three with a Foundation-only core (Codex) | Four libraries and the app. The separate Pro Tools target is the main structural gain. There is no generated catalog: commands are declared in `FloFeatures`. |
| "Ported" column | Hand-edited, or removed | Kept as a frozen record. Its check against the code went with the KM parity tooling once the port was finished. |
| Durable enable state | Not persisted, or persisted | Persist explicit user choices, as KM does: the "Flo Tools Enabled" switch. The temporary Inspector and suspensions are never persisted, and the Inspector start preference still applies. |
| Updates | A URLSession check, a native manifest, or Sparkle | Sparkle 2 (owner, 2026-11-03), feed on the `gh-pages` branch. The shown version (`CFBundleShortVersionString`, the GitHub tag without its `v`) is year.release.fix with `-beta.N` for betas, starting at 2027.1.0-beta.1. Sparkle compares only `CFBundleVersion`, and its comparator treats `2027.1.0-beta.1` as equal to `2027.1.0` (tested 2026-11-03), so `CFBundleVersion` is a separate integer build number that goes up by one with every published build, beta or final, starting at 1, and never repeats. The `-beta.N` suffix is outside Apple's documented format for the short version, which only the App Store enforces. Automatic install, which Sparkle lacks as a separate setting, installs a background download right away instead of on quit. |
| Session text in the log | Private | Logged in the opt-in diagnostic log (owner). |

## 9. Behavior changes on purpose

The port kept every shortcut's behavior except these, which the keymap baselines show.

- Ctrl+Cmd+Left and Right switch track views from launch whenever the Inspector is off (`292a877`); the KM version needed one `/` first.
- `/` and backtick work only in the Mix and Edit windows (`292a877`); with scopes they also stop taking the key elsewhere.
- Releasing backtick always turns the Inspector off.
- AudioSuite keys work only in AudioSuite windows. KM's Audio Suite group took any title containing "Audio Suite:", so a plug-in window such as "Plug-in: Audio Suite: X", or a Mix or Edit window of a session with that in its name, also got the AudioSuite buttons and presets. Pinned in `Routing.txt`.
- A track view press queued while the Inspector was off is dropped if the Inspector turns on before it runs (Codex review of `761eb97`). In KM the Inspector turning on disabled the track view macros, which had the same effect.
- A queued press of a command for some windows is dropped if another window comes to front before it runs, also one of the same kind and title, such as a second instance of one plug-in (Codex review, 2026-11-03). Plug-in and Inspector commands act on the front window, so they would otherwise act on a window the user did not press the key in. This includes a switch between Mix and Edit; any-window commands still run.
- While backtick is held, the track view keys are off in every window, because the Inspector is on. In KM the temporary Inspector turned on only the Inspector keys, so the track view keys still worked outside Mix and Edit; `/` already turned them off everywhere.
- The Inspector pan and volume keys (Ctrl+Cmd+arrows, Ctrl+Shift+Cmd+Left and Right, Ctrl+Opt+arrows) repeat while held, at the system key repeat delay and rate (owner's decision, 2026-11-03); in KM each press moved one step. Each step waits for the previous one to finish, and repeating stops on key release, when the key is no longer down, or when a step fails. `repeats while held` in `Keymap.txt`.
- New plug-in window keys Ctrl+Cmd+Up and Ctrl+Cmd+Down (owner's decision, 2026-11-03): step the current parameter of the loaded plug-in view through its Accessibility slider (AXIncrement, AXDecrement) and speak the new value; held, they repeat like the Inspector volume keys. They work only for parameters the plug-in shows as sliders. KM had no key that changed a parameter.
- New preference "Hold a key for a double press", off by default (owner's decision, 2026-11-03): with it on, holding any single/double key for the hold time (100 to 500 ms in 100 ms steps, default 500) runs its double action as soon as that time passes, also when it is shorter than the double-press timeout; taps and double presses work as before. The engine checks every 20 ms whether the key is still down, so a release before the hold time gives the single action, which still waits for the timeout. KM had no such option.
- Track View Toggled on All Tracks (Opt+-) sends Ctrl+Opt+- to Pro Tools, because Pro Tools 26.10 ignores the Opt+- the KM version sent (checked live 2026-11-03). The hotkey stays Opt+-.

## 10. Not done on purpose

No KM action interpreter, no plugin system for commands, no protocols for mocking Accessibility or VoiceOver, no shell commands at runtime, no telemetry. No buffering of keys pressed before the window title is read (section 3). No caching of watch elements (section 3).
