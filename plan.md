# Flo Tools Swift port: architecture and refactor plan

This is the agreed design for the native port. It merges two independent plans, from Fable (`.pi/jobs/plan-fable/response1.md`) and Codex (`.pi/jobs/plan-codex/response1.md`), with the owner's decisions recorded in `AGENTS.md`. Where the two plans disagreed, section 9 says which way was chosen and why. Read the two source plans for detail and reasoning not repeated here.

## 1. Goal and fixed rules

Refactor the two-macro proof into a structure the remaining macros can be ported into, then port them group by group. Of 274 macros without Flo Mouse, Check for Update is dropped and seven are ported (2026-11-02). The rules in `AGENTS.md` ("Rules that must not change") apply: KM hotkeys and conditions kept unless changed on purpose, checked by `KeyboardMaestroParityTests`, Apple events only for VoiceOver, Accessibility for everything in Pro Tools, spoken text as in the JXA, macOS 13, Swift 6 strict concurrency, Sparkle for updates later.

Flo Mouse is out of scope; it moves to a separate project (owner decision, 2026-11-02). Its group and Toggle Flo Mouse are marked "excluded" in `INDEX.md`, which leaves 274 macros in 10 groups to port. Enable/Disable Flo Tools must not touch Flo Mouse when ported.

The ported macros are re-tested live after every step that touches their path.

## 2. Problems in the current code

This is the diagnosis of the two-macro proof, kept for the reasoning behind the plan; section 10 says which steps have fixed which problem. Both plans found these independently, by reading the code. They are not yet reproduced live.

- Pro Tools knowledge is split between `FloToolsCore/ProTools.swift` and `FloMacros` (`Tracks`). Generic code knows `"Mix:"` and track suffixes.
- Hidden singletons (`MacroEngine.start()` reaches `HotKeyCenter.shared`, `ContextMonitor.shared`; `DoublePress.shared`), so dispatch cannot be tested.
- Double press is coded in each macro with string keys and its own Tink. Expired entries are not cancelled, so an old callback can clear a newer entry, and a delayed single can run after its macro is disabled.
- `MacroAction` is synchronous on the main actor. All AX and AppleScript calls run on the main actor, so a busy Pro Tools freezes hotkeys and the menu. Monitors (meters, plug-in, event start) cannot be written in this shape.
- No error model: AX queries return nil or empty, failed presses are ignored, `unsoloAll` always says "unsoloed all tracks."
- `HotKeyCenter.passThrough` unregisters, posts, sleeps 100 ms and re-registers unconditionally. A key can be lost during a context change, and an obsolete registration can be restored.
- `ContextMonitor` polls every second forever, refreshes synchronously inside the hotkey handler, discards its observer token, and records the PID before observer creation succeeds (so it never retries after permission is granted).
- `otherTriggers` is a list of strings; group identity is by name; macros are registered by raw UID strings.
- `VoiceOver.say` interpolates text into AppleScript source, recompiles every call, swallows errors and logs spoken text as public.
- Preferences: hand-rolled JSON, non-atomic writes, a malformed file silently becomes defaults, and only the timeout is applied.
- Two Python tools repeat plist walking and the key table (also repeated in Swift). Regenerating `INDEX.md` erases the "Ported" column.

## 4. Macro model

- Swift is the source of truth (owner decision, 2026-11-02: KM version retired). Each macro declares `MacroID` (`<group>.<lowerCamelName>`, after its KM group), name, scope, mode condition, triggers and action (section 11). Hotkeys are written as text, `.key("Ctrl+2")`, parsed with the one key-name table. KM UIDs appear only in `reference/`. `KeymapTests` pins every binding and the routing of shared keys in `Tests/Baselines/` (step 8 of section 11 removed the KM parity test). There is no generated Swift catalog.
- `MacroTrigger`: `.hotKey(KeyCombo, KeyPhase)` (pressed or released) and `.statusMenu`. KM's focused-window and application triggers belong only to macros that Swift absorbed into the window observer and `Lifecycle` or dropped, so they are not in the engine (review finding 13, 2026-11-03).
- `Macro(id, body)` or `Macro(id, single:, double:)`. `MacroBody = @Sendable (MacroRun) async throws -> Void`, nonisolated (decided 2026-11-02, see section 9): Pro Tools reads run on `AccessibilityActor`, and speech and engine state are reached with `await` on the main actor, so no macro body blocks the main thread. `MacroRun` is `Sendable` and carries the record, the trigger, the front context, an invocation ID and the engine.
- The engine owns double press, keyed by `MacroID`, through a pure `DoublePressDecider` tested with explicit instants. It plays the done sound (Tink in the JXA) before `double`, as almost every JXA macro does; Speak/Toggle Mute calls `double()` first and then Tink, so a macro can choose Tink after. Repeat events are not taps. Pending singles get a generation number and are cancelled on disable, context invalidation, preferences change and stop.
- `MacroEngine.install(_:)` validates that no ID is installed twice and that no two macros tie: same key and phase, overlapping scopes and mode conditions, and the same precedence (Keyboard Maestro showed a conflict palette; here the winner would otherwise depend on install order). Unported macros are not installed, so their keys stay free.
- Enable state separates macro enabled, the Inspector mode, and automatic suspension reasons (VoiceOver not running, Keyboard Shortcuts window open). Removing one suspension reason does not clear another or override a user choice. The one persisted user choice is the "Flo Tools Enabled" switch, kept by `PreferencesStore.floToolsEnabled` (2026-11-02); suspensions are not persisted. Macro enables set by preferences (Toggle Temporary Inspector) are derived state, not user choices. Group enable and activation state were removed with the groups (section 11).
- `engine.run(_:)` runs a macro directly, for the status menu. Macros do not run other macros; shared behavior is a shared Swift function (section 11, step 6).
- Mutating Pro Tools operations run through one foreground queue so two macros cannot interleave across `await`. A queued hotkey run checks when it starts that Flo Tools and the macro are still enabled, that its scope still applies to the current context, and that the front app is still the process it was accepted for; otherwise it is dropped and logged. It does not check the mode, so a single press of S accepted while the temporary Inspector key was held still speaks after the release; and there is no context generation number, because a run accepted in Mix that starts in Edit is still valid for every Inspector macro (Codex, step 4 design check). The temporary Inspector release is cleanup: the hold is recorded when the key event arrives and cleared on release, focus loss, disable and stop, outside the foreground queue. `Monitors` holds one tracked task per monitor; `engine.cancelAll()` implements Cancel Macros.
- Macro families share one parameterized implementation (send slots, insert slots, fade dialogs, counters, track lists, plug-in navigation). Sends and inserts keep separate layout rules because their AX layouts differ.

## 5. System layer

- Accessibility: `AXElement` isolated to a global `AccessibilityActor`, so a busy Pro Tools blocks that actor and not the main actor. Typed attributes, role-filtered child lists and filters that match the JXA vocabulary (`buttons[2]`, `groups.byName`, `whose`), with batched attribute reads. Immediate-child lookups never fall back to a whole-tree search. Messaging timeout 1 s global and on the Pro Tools application element; tune from live measurement. Macro bodies are nonisolated, so every Pro Tools read is an `await` on this actor and returns small value types.
- Errors: queries return optionals for ordinary absence. `FloProTools` turns a missing required element into a thrown `FloError` with `required(_:)`. AX actions (`press`, `perform`, `set`) throw with the `AXError`. A failed read is never treated as "off".
- One error model: `FloSystem` defines `FloError` (cases for AX failures with the `AXError`, VoiceOver failures, timeouts and `notFound(what:)`; cancellation stays Swift's `CancellationError`). `ProToolsError` and the former `VoiceOverError` are not separate types; `FloProTools` throws `FloError` with Pro Tools-specific descriptions (window missing, no track under cursor). `MacroError` is dropped. This keeps `FloEngine` free of a `FloProTools` import.
- What the user hears on failure is decided in one function in the engine (`SpokenError`), which switches on `FloError`. Cancellation is silent. A failure to speak an error is logged, never retried by speaking.
- VoiceOver: `say` and `cursorText` send VoiceOver's Apple events directly (`NSAppleEventDescriptor`, no AppleScript source), with the text as a parameter and a 2 s timeout per call. About 3 ms per call instead of about 30 ms for compiled AppleScript (measured 2026-11-02). `escape` is removed. Errors throw `FloError.voiceOver`; `sayOrLog` is for the app's own messages and the engine's spoken failures, which have nobody to report to.
- Hotkeys: Carbon `RegisterEventHotKey` stays, with context-dependent registration, press and release events, and the instance reached through `refcon`. Pass-through and simulated keystrokes use `CGEvent.postToPid` to the front app, with no unregister and re-register window. Every synthetic event carries a Flo Tools `eventSourceUserData` marker.
- Context: `FrontWindowObserver` and `ApplicationObserver` are instances with explicit `start()` and `stop()`. `FrontContext` adds PID and window identity so window changes and title changes are distinguishable. AX notifications drive refreshes; a slow poll runs only while no observer is attached; failed attachment is retried. Context is read off the main actor, never synchronously inside the hotkey callback.
- Logger: one `Log` used everywhere. Warnings and errors in the unified log are marked private, because they can carry track names, which the owner approved only for the opt-in file. It is specified in `AGENTS.md` ("Diagnostic log"): "Turn On Log" and "Turn Off Log" menu item, file in `~/Library/Logs/Flo Tools/` revealed in Finder on turn-off, header with versions, permissions, preferences and group state, invocation IDs on every line, per-step AX trace and subtree dumps where a lookup fails.

## 6. Pro Tools layer

`FloProTools` is the one place where System Events paths become named things: `ProToolsApp.running()`, `mix()`, `edit()`, `plugIn()`, `audioSuite()`, `fadeDialog()`, `menuBar()`, `keystroke(_:)`; `MixWindow.trackStrips()`, `trackUnderVoiceOverCursor()` (the one place the VoiceOver cursor is joined to a strip), `hasActiveGroups()`; `TrackStrip` with name, kind, solo, mute, record arm, `send(_:)`, `insert(_:)`, volume, pan, meters, comments; `EditWindow` counters, grid, nudge; and so on. Reads return small value structs so the next step is a pure function.

Unsolo All Tracks is hardened as the model for multi-step mutations: validate the window and process, read eligible tracks (excluding master, safe, inactive), suspend groups and verify, process ordinary tracks before folders, revalidate each target before toggling, restore group state on completion, error or cancellation, and announce success only after full success. Partial completion is reported as such.

## 7. Preferences and state

- Preferences live in UserDefaults, read once by `PreferencesStore` at launch and passed down; the preferences panel is the only writer. The owner decided on 2026-11-02 that the KM `flotools.json` is neither read nor migrated, since the KM version is retired. Missing values are defaults; a timeout outside 200/300/400/500 (only possible with `defaults write`) is logged and replaced by 200. Tests use a throwaway UserDefaults suite.
- `FloMacros.apply(_:to:)` is the single home of KM's "Refresh Preference" (timeout, temporary Inspector). The menu item "Preferences…" and the "Flo Tools Preferences" macro (Ctrl+Cmd+,) open the same AppKit panel (two checkboxes, timeout popup 200/300/400/500, OK and Cancel). "Reload Preferences" is gone: nothing else writes the settings.
- Transient KM variables become typed state owned by the macro family that uses it, reset at the matching lifetime boundary (Pro Tools quit, window change).
- Plug-in view files keep their JSON-in-`.txt` format and location; filenames from window titles are sanitized to one path component.

## 8. Tooling, packaging, tests

The reference generator and the parity test described below were removed in section 11, step 8; `reference/` stays as generated.


- `tools/km_export.py` replaces `gen_catalog.py` and `extract_macros.py` and only writes `reference/macros/`; `--check` fails on a diff. It keeps the "Ported" column from the existing `INDEX.md` when regenerating, and confines deletion to `reference/macros/`. Add standard-library Python tests.
- The key-name table exists in Swift (`KeyNames.swift`) and in `km_export.py` for the reference files. They are separate outputs of a frozen export, so a shared generated table is not worth the machinery.
- `KeyboardMaestroParityTests` reads `reference/macros/INDEX.md` and fails if the "yes" entries of the "Ported" column do not match `macroOrigins`, so the column cannot drift from the code.
- `scripts/build-app.sh` fails when no signing identity is found instead of falling back to ad hoc; `FLO_SIGN_IDENTITY=-` asks for ad hoc explicitly.
- Unit tests (deterministic, no sleeps for synchronization; the cancellation test waits for a started signal and the crash report test dates its old file back): KM parity, routing and specificity, enable and suspension state, trigger matching, double-press decisions, runner (nesting, cycles, cancellation, partial failure), error-to-speech table, preferences JSON, and per-area text and parsing.
- Live tests in Pro Tools as in `AGENTS.md`, plus `scripts/live-test.sh` (press a key through System Events, print the last VoiceOver phrase and the log line). Plan-specific live checks: synthetic keys posted to a PID do not re-trigger hotkeys, AX timeout behavior with Pro Tools busy, temporary Inspector hold with a physical keyboard, fade dialog groups active on the first key press, monitors stop on title change and Pro Tools quit, permission granted later recovers without relaunch.

## 11. Native redesign (decided 2026-11-03)

The port is complete, but its structure still copies Keyboard Maestro: groups with title conditions, macros enabled and disabled to swap keys, "specificity" with no tie rule, and macros calling macros by ID. Codex (`.pi/jobs/native-design-codex/response1.md`) and Fable (`.pi/jobs/native-design-fable/response1.md`) reviewed it; the owner decided the open questions on 2026-11-03 (journal J-89). The redesign keeps every shortcut's behavior except the deliberate changes below, which the keymap baseline shows as diffs.

### Model

- `Command`: what a key does (ID, name, action). Feature files declare commands and their bindings; "macro" is used only for Keyboard Maestro artifacts.
- `Binding`: key and phase, scope, mode condition, command. A scope is "any Pro Tools window" or a set of `ProToolsWindow.Kind`s.
- `ProToolsWindow.Kind` in `FloProTools`: one kind per window, from one classification function over the title (Mix, Edit, Plug-in, AudioSuite, Fade In, Fade Out, Crossfade, Batch Fades, setup tab, other). The order of checks lives only there; a title starting with "Plug-in:" is a plug-in window even if it also contains "Audio Suite:". With one kind per window, ties can be proved absent.
- `Keymap`: all bindings, indexed by key. Precedence: a binding for specific window kinds beats an any-window binding. Two bindings for the same key, phase, window kind and mode are an error at install time and in the tests, instead of depending on declaration order.
- `Mode`: app state the keymap reads, so far only the Inspector (on or off). The temporary Inspector is a hold that turns it on and, on release, always off. Track view keys are bindings that apply while the Inspector is off, so nothing enables or disables commands to swap keys.
- Shared behavior is shared Swift functions, not one command running another by ID; nested runs and their cycle check go.
- `FloEngine` imports `FloProTools` for `ProToolsWindow.Kind`. A protocol in the engine with one Pro Tools implementation would only add a layer; Flo Tools drives only Pro Tools.

### Behavior changes on purpose

- Ctrl+Cmd+Left/Right run track view from launch whenever the Inspector is off (done `292a877`; the KM version needed one `/` first).
- `/` and backtick work only in Mix and Edit windows, `^(Mix|Edit):` (done `292a877` inside the command; with scopes they also stop taking the key elsewhere).
- Releasing backtick always turns the Inspector off, as today.
- AudioSuite keys work only in AudioSuite windows (step 4). KM's Audio Suite group took any title containing "Audio Suite:", so a plug-in window such as "Plug-in: Audio Suite: X" or a Mix or Edit window of a session with that in its name also got the AudioSuite buttons and presets.
