# Flo Tools: architecture

This is the agreed design of the native app, described as the code has it now. It began as the merge of two plans, by Fable (`.pi/jobs/plan-fable/response1.md`) and Codex (`.pi/jobs/plan-codex/response1.md`), followed by a native redesign that both reviewed (`.pi/jobs/native-design-codex/response1.md`, `.pi/jobs/native-design-fable/response1.md`) and the owner decided on 2026-11-03 (journal J-89). The port and the redesign are finished. Their step-by-step sequence and the diagnosis of the first two-macro proof are in git history (this file before 2026-11-03's rewrite) and in the journal.

## 1. Goal and fixed rules

Flo Tools is a menu bar app that makes Pro Tools usable with VoiceOver by driving it through the Accessibility API. It replaces the Keyboard Maestro (KM) macro library, which is retired. The KM export in `reference/` is a frozen record of how each macro was ported (`reference/macros/INDEX.md`, "Ported" column).

The rules in `AGENTS.md` ("Rules that must not change") apply: hotkeys and windows are kept unless changed on purpose (section 9) and are pinned by `KeymapTests`; Apple events only for VoiceOver; the Accessibility API for everything in Pro Tools; spoken text as in the JXA unless a reason is stated; macOS 13; Swift 6 strict concurrency; Sparkle for updates. Flo Mouse is out of scope and moves to a separate project (owner decision, 2026-11-02).

## 2. Targets and dependency direction

| Target | Owns | Depends on |
|---|---|---|
| `FloSystem` | Generic macOS infrastructure: `AXElement` and `AccessibilityActor`, `VoiceOver` and `VoiceOverActor`, `HotKeyCenter`, `KeyCombo` and the one key-name table, `Keyboard`, `Mouse`, `FrontWindowObserver`, `WorkspaceEvents`, `Sound`, `SystemSpeech`, Flo Tools' own windows (`Chooser`, `TextWindow`), `PrivacyPermission` (resetting Flo Tools' own privacy entries), `FloError`, `Log` | Apple frameworks |
| `FloProTools` | Pro Tools knowledge: `ProToolsApp`, `ProToolsWindowKind`, `MixWindow`, `TrackStrip`, `TrackList`, `EditWindowControl`, `ProToolsSetting`, `PlugInWindow`, `FadeDialog`, the front window facts and `AnnouncementGuard`, `ProToolsKeyCapture` (whether a menu or a field open for typing takes Pro Tools' keys), `ProToolsUpdate` (waiting for Pro Tools to show a change) | `FloSystem` |
| `FloEngine` | The command model and runtime: `Command`, `CommandID`, `Trigger`, `Scope`, `CommandRun`, `Engine`, `Watches`, `SpokenError`, `FrontContext`, `Preferences` and `PreferencesStore` | `FloSystem`, `FloProTools` |
| `FloFeatures` | The commands, one folder per feature; `FloFeatures.all`, `SessionState`, `Lifecycle`, the plug-in view installer | `FloSystem`, `FloEngine`, `FloProTools` |
| `FloTools` | The app: `AppDelegate`, status menu, permission prompts, the preferences panel, the diagnostic log header, Launch on Login | all of the above |

Nothing below `FloFeatures` knows a command by name. `FloEngine` imports `FloProTools` because a scope names Pro Tools window kinds; a protocol in the engine with one Pro Tools implementation would only add a layer, and Flo Tools drives only Pro Tools. There are no protocols for mocking: dependencies are concrete instances passed through initializers or captured by closures. The only shared instances are the two global actors, which Swift requires to have one.

## 3. Command model

- A `Command` has an ID (`CommandID`, such as `inspector.speakToggleSolo`, kept from the KM group and macro), a name, a summary for `COMMANDS.md`, a scope, triggers and an action. Feature files declare their commands, and `FloFeatures.all` lists them. "Macro" is used only for Keyboard Maestro artifacts, and KM UIDs appear only in `reference/`.
- Triggers are `.key("Ctrl+2")`, a hotkey parsed by `KeyCombo(literal:)`, and `.statusMenu`. A key's release starts nothing; it ends repeating and tells a tap from a hold. KM's focused-window and application triggers belonged to macros that `Lifecycle` and the window observer absorbed, so the engine has none.
- A `Scope` is any Pro Tools window, a set of `ProToolsWindowKind`s, or the track under the VoiceOver cursor. Each front window title has exactly one kind, from one classification function in `FloProTools`: Mix, Edit, Plug-in, AudioSuite, Fade In, Fade Out, Crossfade, Batch Fades, setup tabs, Keyboard Shortcuts, New Tracks, other. The order of checks lives only there; a title starting with "Plug-in:" is a plug-in window even if it also contains "Audio Suite:". With one kind per window, ties can be proved absent.
- The Inspector keys are scoped to the track under the VoiceOver cursor (`Scope.trackUnderVoiceOverCursor`), in the Mix or Edit window. Only a press can tell whether the cursor is on a track name, so the engine checks at each press. On a track, the command runs on that track. Otherwise the key goes to the next command that has it in that window, such as the track view commands of Ctrl+Cmd+Left and Right, or on to Pro Tools. This replaces KM's Inspector mode with its `/` and backtick keys (owner, 2026-11-08, section 9); no state decides which keys apply, and no command enables or disables another to swap keys.
- The engine indexes commands by key. A command for the track under the cursor beats a command for window kinds, which beats an any-window command. Two commands for the same key with the same precedence in overlapping windows are an error at install and in the tests, instead of depending on declaration order; a duplicate ID is too. `Binding` and `Keymap` are not types of their own, because every command's keys share one scope. A separate binding would be worth it only once one command needs different windows per key.
- While Pro Tools is in front but its window title is not read yet (about 35 ms after activation, J-105), a key that some window kind gives to a command of its own is not taken, so its any-window command cannot run in the wrong window; it goes on to Pro Tools like the other window-only keys (Codex context-gap review, 2026-11-03; today only Shift+Up and Shift+Down, which Batch Fades overrides). Keys pressed in that gap are not held back and routed later: replaying them would reorder them against keys Pro Tools gets directly and lose hold durations, and would need an event tap that buffers the whole keyboard stream.
- An action is a body, a tap and hold pair, or a body that repeats while its key is held. Bodies are `@Sendable (CommandRun) async throws -> Void` and nonisolated (owner, 2026-11-02): Pro Tools reads run on `AccessibilityActor`, speech on `VoiceOverActor`, and engine state on the main actor, so no body blocks hotkeys or the menu. `CommandRun` carries the command, its origin (hotkey, run by the app, or an event), the front context and the engine. Its invocation ID for the log is `Log.invocation`, which the tasks it starts inherit.
- The engine tells a tap from a hold. A key with a tap and a hold action that stays down for the hold time from the preferences runs its hold action as soon as that time passes, timed from when the key went down; letting go sooner runs the tap at once. The release event ends the wait, and the physical key state is checked every 20 ms for a release event that never arrives. A new press of the key runs a tap still waiting first. A status menu or event run runs the tap. A command chooses whether the done sound (Tink in the JXA) plays before or after its hold action, or not at all. Waiting taps are voided with the other pending input (below).
- Commands run through one serial queue, so two cannot interleave across `await`. A queued hotkey or event run checks when it starts that Flo Tools and the command are still enabled, that its scope still applies, that the front app is the process it was accepted for and, for a command scoped to some windows, that the same window is in front; otherwise it is dropped and logged. A run on the track found at its press is also dropped once that press's input generation is voided, because the track may be out of date.
- Every key press goes through one ordered main-actor admission chain before the command queue, so a later press, even of a key that needs no cursor check, never starts before an earlier press's check ends. A press of a key with no track command waits only for earlier admissions. The cursor and key capture checks run off the main actor and share the press's invocation ID. Logs of a key passed on omit the key; only a command run logs its key. Each admitted press records when the key went down, its context, the input generation and its own release state. Releases are not queued and end repeating at once. A change of context, enable state, suspension or hold time, cancel and stop void the input generation: admissions still checking, taps waiting to tell a tap from a hold, and repeating started on a track. Only a still-valid result may start a command or pass a key on. When the cursor check fails, it counts as off a track and is logged. A key capture passes the key on to Pro Tools even when the cursor check finds a track, as does a capture check that fails (right if a field is open, harmless if not), because the VoiceOver cursor still reports the track behind a menu opened from it (seen live 2026-11-07 after double T) and behind a counter opened for typing (double Cmd+F1). `ProToolsKeyCapture.check` (FloProTools, fed the front app's notifications by `ContextMonitor`'s one observer) returns `.menu` between AXMenuOpened and AXMenuClosed from the front app, or while the app shows a pop-up menu window; the notification comes first, the window check covers a menu opened before the observer attached. A missed AXMenuClosed would keep forwarding until the front app changes or the next menu closes. It returns `.textField` in two cases. The app's focused element is a text entry (`hasTextEntryFocus`), as the editor opened by a Mix comments field is. Or the element of the app's last AXSelectedTextChanged, with no AXFocusedUIElementChanged since, is a text field whose own AXFocused is set. Pro Tools sends AXSelectedTextChanged when it opens a counter, tempo, nudge or pre/post-roll field for typing, but does not make the field the app's focused element and sends no focus notification on opening; closing it does send one. The remembered field is forgotten on any focus change because a Mix comments field kept AXFocused set after its editor closed (seen live 2026-11-07), which would otherwise capture keys indefinitely. Scanning every text field for AXFocused also works but took about 400 ms; reading the focused element and one remembered field at key time is two AX reads. The check runs after detection, the last moment before deciding.
- `FloProTools` detects a track-name cursor from a paired `VoiceOverActor` text/bounds read, then a track-name suffix plus exact text and frame equality with one uniquely named immediate AXGroup of the focused Mix/Edit window. Its name must end with the case-insensitive pattern ` - (?:\w+ )+track\s*$`, which accepts multiword folder types and trailing whitespace but rejects unrelated groups such as Counter Display Cluster (owner, 2026-11-07). Containment, invalid bounds and duplicate names are rejected. The named-group representation and rejection of neighboring controls were checked live in both Mix and Edit. Name pop-ups are not accepted without live evidence. Accepted targets retain the source AX identity and exact name; delayed actions check that the accepted group still exists with its name (one read, not a scan, so a press does not cost a read per strip twice) and use it when the command acts in the same window, or the uniquely named strip in the other window. Repeats keep the accepted target. Meter watches retain their separate cursor-following lookup.
- A hold is timed from when the key went down, even when the cursor check delays the start. A release during the check makes the press a tap and starts no repeating. Only presses of keys Flo Tools takes can be ordered; keys it does not take go straight to Pro Tools. Forwarding uses the existing balanced synthetic tap and does not preserve physical hold duration or native autorepeat; phase-preserving forwarding would require a separate input design and physical validation.
- `Watches` holds one task per watch, such as the level meter, the plug-in monitor and the MIDI event column, outside the queue. They poll every 100 ms, because Pro Tools sends no Accessibility notification for many value changes (checked live for preset changes). The plug-in monitor finds its sliders again on each poll; keeping them was measured (J-176) and rejected, because the gain was small and a stale element would read a closed window. Two watches keep an element for a bounded time: the meter watch keeps the strip while the name under the VoiceOver cursor stays the same, and the MIDI event watch keeps its field for `readsPerLookup` reads (one second) and finds it again after a failed read. `engine.cancelAll()` stops the queue and the watches, like KM's Cancel Macros.
- Shared behavior is a shared Swift function, not one command running another. Command families share one parameterized implementation: send and insert slots, fade dialogs, counters, track lists, plug-in navigation and passed-on shortcuts. Sends and inserts keep separate layout rules, because their Accessibility layouts differ.
- Enable state keeps apart the user's "Flo Tools Enabled" switch (persisted by `PreferencesStore`) and suspension reasons: VoiceOver not running, and the Pro Tools Keyboard Shortcuts window open, kept while that window exists behind another, as in KM. Removing one reason does not clear another or override the user's choice. Suspensions are not persisted.

## 4. System layer

- Accessibility: `AXElement` is isolated to the global `AccessibilityActor`, so a busy Pro Tools blocks that actor and not the main actor. It has typed attributes, role-filtered child lists and lookups in the JXA vocabulary (`groups`, `button(_:)`). Immediate-child lookups never fall back to a whole-tree search. The global messaging timeout is 1 s. A press that may open a pop-up menu uses 0.25 s on that element, because Pro Tools answers it only when the menu closes, and counts a timeout as done when a menu window is then on screen.
- Reads: only "no value" and "no such attribute" are absence; any other `AXError`, such as a busy app or a closed window, throws. A failed read is never treated as "off". A lookup a command cannot continue without goes through `AXElement.required`, which throws `FloError.notFound` and, while the log is on, logs a bounded dump of where the lookup stopped. Actions throw with the `AXError`.
- One error model: `FloSystem` defines `FloError`, with cases for Accessibility failures, VoiceOver failures, timeouts, missing elements and actions that could not be done. `FloProTools` throws it with Pro Tools descriptions, such as a missing window or no track under the cursor. What the user hears is decided in one table in the engine, `SpokenError`. Cancellation is silent. A failure to speak an error is logged, never retried by speaking.
- VoiceOver: `say` and the cursor reads send VoiceOver's Apple events directly (`NSAppleEventDescriptor`, no AppleScript source), with the text as a parameter and a 2 s timeout per call, about 3 ms per call instead of about 30 ms for compiled AppleScript (measured 2026-11-02). They run on `VoiceOverActor` (section 8). The one warning VoiceOver cannot speak, that it does not take Flo Tools' Apple events, goes through `SystemSpeech`.
- Hotkeys and synthetic keys: Carbon `RegisterEventHotKey`, registered for the current context, with press and release events. Passing a key on and sending keystrokes post to Pro Tools' process with `CGEvent.postToPid`, through one serial queue, with a 10 ms hold because Pro Tools ignores a key down followed at once by its key up. Every synthetic event carries `Keyboard.syntheticMarker`. Events come from a private event source: a key posted from inside a hotkey press with the HID system state source reached the Dock but made it select its first item, and a private source worked (checked 2026-11-08; cause unknown). Keys are registered by the front app, but another process can hold the keyboard while the front app stays active: the Dock under VoiceOver (VO+D) and Spotlight do. So every press first reads the system-wide focused application (0.4 to 17 ms measured); when it is a different known process, the press is posted to that process and runs no command. Only the Dock sends a notification for this, so a read at key time covers every such case without a list. When the read fails, keys go by the front app, as before. A key typed system-wide would be caught again by the hotkeys, so passing on stays `postToPid`.
- Mouse: events go to the window under the pointer, so they are posted to the whole system. Each operation names the app it is for and posts nothing when another app has come to front meanwhile, for example while the command was speaking. The check narrows the race rather than closing it.
- Context: `FrontWindowObserver` attaches Accessibility notifications (focused window changed, title changed, menu closed) to the front app and polls only while not all of them are registered, retrying on every read. Reads run on `AccessibilityActor`; the front app's process is published at once with an unknown title, and a read's result is dropped if a change was reported while it ran (`WindowTitleReads`, tested without Accessibility). `FrontContext` carries the process, the window number, the title and the window kind. `WorkspaceEvents` reports app launch and quit and VoiceOver on and off. The observer’s C callback is explicitly nonisolated because the main run loop delivers notifications outside the AccessibilityActor executor; it only converts the event and calls the Sendable handoff.
- Logger: one `Log` in `FloSystem/Log.swift`; nothing calls `Logger` or `print` directly. Its purpose is a file users can send that shows where a command failed.
  - One menu bar item switches between "Turn On Log" and "Turn Off Log"; logging is off by default. Turning it on opens a new file in `~/Library/Logs/Flo Tools/` named for the current time (`Flo Tools 2026-11-07 19-14-02.log`). The on state survives relaunches and crashes, and each launch with logging on opens a new file the same way, because an app can read back only its own current process's unified log. Turning it off closes the file and reveals it in Finder, selected (`NSWorkspace.activateFileViewerSelecting`).
  - The file starts with a header: app version and build, macOS and Pro Tools versions, whether VoiceOver is running, permissions, preferences, suspension, and Launch on Login (off, or the program the launch agent starts). Flo Tools crash reports from `~/Library/Logs/DiagnosticReports` written while logging was on are appended, with `crashReporterKey`, `deviceIdentifierForVendor` and `bootSessionUUID` redacted. Nothing is uploaded.
  - While on, every entry is written at full detail, except debug entries inside watch polls and the front window poll (`Log.skipsDebug`), which at ten polls a second would fill the file; their changes, speech and failures are still logged. The file is capped at 20 MB: past it, the oldest entries are dropped down to 19 MB, keeping this launch's header at the top, and the drop is logged. A batch rather than one entry at a time, because each drop rewrites the file. Earlier files are not deleted. While off, nothing is written to a file, and only warnings and errors go to the unified log (subsystem `com.chikim.FloTools`, one category per area), marked private because they can carry track names, which the owner approved only for the opt-in file.
  - One line per entry: timestamp with milliseconds, level, category, invocation ID, message. Each run logs its trigger and routing decision (context, chosen command, or why the key passed through), each Accessibility step with selector path, result, `AXError` and duration, speech requests and VoiceOver errors, and the final result, error or cancellation with total duration. A missing required element logs the bounded subtree where the lookup stopped (role, title, description, index, a few levels deep). App start and stop, permission, context, enable and suspension changes, preferences loads, and helper or event-tap failures are logged too.
  - Track names, window titles, session names and spoken text may be logged (owner, 2026-11-02). File writes happen on a serial background queue, and the event-tap callback only enqueues.

## 5. Pro Tools layer

`FloProTools` is the one place where Accessibility paths become named things: `ProToolsApp.running()`, its windows (`mixWindow()`, `trackWindow(_:)`, `plugInWindow(_:)`, fade dialogs), `TrackStrip` with name, kind, solo, mute, record arm, sends, inserts, volume, pan, meters and comments, `TrackList`, Edit window controls such as counters, grid and nudge, settings in menus and toolbars, and `keystroke(_:)`. Reads return small value types, so the next step is a pure function that unit tests can cover.

Unsolo All Tracks is the model for multi-step changes: check the window and process, read the eligible tracks (not master, safe or inactive), suspend the groups and confirm it in the Group List, process ordinary tracks before folders, check each track again before clicking, resume the groups on completion, error or cancellation, and announce success only after full success. Partial completion is reported as such.

## 6. Preferences, lifecycle and state

- Preferences live in UserDefaults (`com.chikim.FloTools`), read once by `PreferencesStore` at launch and passed down; the preferences panel is the only writer. The KM `flotools.json` is neither read nor migrated (owner, 2026-11-02). Missing values are defaults; a hold time outside 100, 200, 300, 400 and 500 ms (only possible with `defaults write`) is logged and replaced by 200. Tests use a throwaway suite that they delete.
- `FloFeatures.apply(_:to:)` is the one home of KM's Refresh Preference, which now sets only the hold time. KM's "starts with Flo Tools inspector" and "use temporary inspector" went with the Inspector mode (section 9). The menu item "Preferences…" and the Flo Tools Preferences command (Ctrl+Cmd+,) open the same panel.
- `Lifecycle` replaces KM's Global group, because those macros change Flo Tools itself and must work while it is suspended: suspending while VoiceOver is off or the Keyboard Shortcuts window is open, `cancelAll()` on Pro Tools quit, stopping the meter watches on a window change, and on Pro Tools launch applying the preferences; session state resets on quit. Only Flo Tools' startup announcement checks VoiceOver communication; there is no separate silent check on Pro Tools launch. A plug-in window coming to front, or changing its title to another plug-in, loads that plug-in's default view.
- Transient KM variables became typed state in `SessionState`, owned by the feature that uses it and reset at the matching boundary (Pro Tools quit, window change). A clip mark records its Edit window and is dropped when that window is gone.
- Updates: `Updater` in the app target wraps Sparkle's standard controller and builds the Updates submenu: the version as a dimmed label, Check for Updates, and four settings. Automatically Check and Automatically Download are Sparkle's own settings, which it keeps in UserDefaults. Automatically Install (install a background download now and relaunch, not on quit) and Include Beta (allow the appcast's `beta` channel) are `PreferencesStore` keys. A setting that depends on one that is off is dimmed. Flo Tools has no Dock icon, so Sparkle shows a scheduled update's window behind the front app; VoiceOver says that an update is available instead. The feed is `https://flotools.org/flotools/appcast.xml` (`appcast.xml` on `gh-pages`), signed with the EdDSA key in the owner's keychain, whose public half is `SUPublicEDKey`. A release adds one `<item>`: set `CFBundleShortVersionString` and raise `CFBundleVersion` by one in `Info.plist`, build with `FLO_SIGN_IDENTITY="Developer ID Application: …" scripts/build-app.sh` (a Developer ID identity also gets a secure timestamp), submit a `ditto` zip with `xcrun notarytool submit --keychain-profile "FloTools Installer-notary" --wait`, staple the app, zip with `ditto -c -k --keepParent`, upload the zip to a GitHub release, run `.build/artifacts/sparkle/Sparkle/bin/sign_update` on it for `sparkle:edSignature` and `length`, and add `sparkle:version` (the build number), `sparkle:shortVersionString`, `sparkle:minimumSystemVersion` 13.0 and, for a beta, `<sparkle:channel>beta</sparkle:channel>`. Tag the release `v` plus the shown version, and mark a beta as a GitHub pre-release.
- Launch on Login: `LoginItem` in the app target writes a launch agent, `~/Library/LaunchAgents/com.chikim.FloTools.plist`, as VOCR does (owner, 2026-11-05; an `SMAppService.mainApp` version came first and was replaced). The file is the setting. Unlike VOCR's shipped plist, whose `Program` is fixed to `/Applications`, the agent is written when the setting is turned on and names the executable of the copy that turned it on (`RunAtLoad`, `LimitLoadToSessionType` Aqua, no `KeepAlive`). Known limits: if that copy is moved or deleted, the file stays and still reads as on; macOS 13 and later list the agent under "Allow in the Background" in System Settings > Login Items, and turning it off there leaves the file, so the panel still shows it on. It is on by default: the first launch from `/Applications` or `~/Applications` turns it on once (`launchOnLoginOffered`), after which it stays as the user leaves it. A copy run from elsewhere (Downloads, a disk image, `build/`) does not turn it on, because the agent would run that copy. "Launch on Login" is the first checkbox of the preferences panel; OK writes or removes the file, and the panel reads it each time it opens.
- Plug-in view files keep the KM format (JSON in `.txt`) and location, `~/Library/Application Support/Flo Tools/Plug-In Views/`. Filenames from window titles are sanitized to one path component. The app copies the views it ships there on first launch, without overwriting the user's files. Views added in a later version do not reach users who already have them installed; a Sparkle update does not change this.

## 7. Tests and tooling

- Unit tests are deterministic, with no sleeps for synchronization. They cover routing and precedence, the tie check, enable and suspension state, tap and hold decisions, the track-under-cursor check and its fallback, the queue and cancellation, error wording, preferences, window classification, title read ordering, the log file, and per-feature text and parsing.
- `KeymapTests` pins every binding and the routing of shared keys in `Tests/Baselines/Keymap.txt` and `Routing.txt`. `CommandReferenceTests` generates `COMMANDS.md` and fails when it is out of date. Both regenerate with `FLO_WRITE_BASELINES=1`.
- `scripts/build-app.sh` fails when no signing identity is found instead of falling back to ad hoc; `FLO_SIGN_IDENTITY=-` asks for ad hoc explicitly. `--release` raises `CFBundleVersion` by one and commits it before building, and only with a Developer ID identity and no uncommitted changes to tracked files, so every published build has a new number and matches a commit. Test builds keep the number, because Flo Tools is rebuilt many times a day and a bump on every build would change a tracked file each time.
- Live tests in Pro Tools follow `AGENTS.md`. `scripts/vo.sh` reads and moves the VoiceOver cursor through VoiceOver's AppleScript dictionary and invokes VoiceOver commands by name.

## 8. Decisions and their reasons

| Topic | Options | Decision |
|---|---|---|
| Key input | Carbon hotkeys with `postToPid` (Fable), or one `CGEventTap` (Codex) | Carbon with `postToPid`: the smaller change, it keeps the working path and needs no new permission. Carbon supports hotkeys without modifiers and release events. Holds are tracked apart from routing. The synthetic marker is for logs only; Carbon hotkey events do not carry it. Switch to an event tap only if a live check fails. A physical keyboard check is still open. |
| VoiceOver isolation | Main actor (Fable), or a separate helper executable (Codex) | A dedicated global actor, `VoiceOverActor` (2026-11-03, Codex infrastructure survey). A helper adds a second signed executable and IPC for a risk not yet seen, but the main actor was wrong too: each call waits up to its 2 s timeout, and an unresponsive VoiceOver then held up hotkey routing, key releases and the menu. Each caller awaits its calls, so its own speech stays in order; separate callers get no first-come order. Still to check live: VoiceOver unresponsive while keys are pressed. |
| Accessibility threading | Global actor (Fable), or a thread with its own run loop (Codex) | Global actor: simpler and enforced by the compiler. The messaging timeout bounds each call, not a whole traversal, so long jobs such as Unsolo All check for cancellation between operations. Observers keep an explicit run-loop owner. |
| Command body isolation | Nonisolated bodies, or main-actor bodies | Nonisolated (owner, 2026-11-02). A main-actor body would block hotkeys, the menu and key releases whenever Pro Tools is slow; the cost is an `await` on each Pro Tools read. |
| Targets | Four libraries (Fable), or three with a Foundation-only core (Codex) | Four libraries and the app. The separate Pro Tools target is the main structural gain. There is no generated catalog: commands are declared in `FloFeatures`. |
| "Ported" column | Hand-edited, or removed | Kept as a frozen record. Its check against the code went with the KM parity tooling once the port was finished. |
| Durable enable state | Not persisted, or persisted | Persist explicit user choices, as KM does: the "Flo Tools Enabled" switch. Suspensions are never persisted. |
| Updates | A URLSession check, a native manifest, or Sparkle | Sparkle 2 (owner, 2026-11-03), feed on the `gh-pages` branch. The shown version (`CFBundleShortVersionString`, the GitHub tag without its `v`) is year.release.fix with `-beta.N` for betas, starting at 2027.1.0-beta.1. Sparkle compares only `CFBundleVersion`, and its comparator treats `2027.1.0-beta.1` as equal to `2027.1.0` (tested 2026-11-03), so `CFBundleVersion` is a separate integer build number that goes up by one with every published build, beta or final, starting at 1, and never repeats. The `-beta.N` suffix is outside Apple's documented format for the short version, which only the App Store enforces. Automatic install, which Sparkle lacks as a separate setting, installs a background download right away instead of on quit. |
| Session text in the log | Private | Logged in the opt-in diagnostic log (owner). |
| Permission recovery | Point the user to System Settings, or reset Flo Tools' own entry with `tccutil` | Reset with `tccutil` (owner, 2026-11-07). Without a recorded Automation answer, VoiceOver sometimes asks macOS about Flo Tools while Pro Tools is busy, and that dialog closes after 2 seconds; a recorded Allow stops it, and a Don't Allow makes some VoiceOver events fail. macOS asks only once, so "Allow Control of VoiceOver…" resets a refusal and asks again, and "Grant Accessibility Access…" resets an off or stale entry before opening the Accessibility list. Both sit in a Permissions submenu with "Reset All Permissions…", which confirms, resets every Flo Tools entry and relaunches, because a running process keeps its Accessibility trust until it quits (seen 2026-11-07). There is no public API for a reset; `tccutil` is a system tool not documented for apps. It works for an unsandboxed app's own entries without administrator rights (tested 2026-11-07), and an AppleEvents reset clears the answers for every target app, today only VoiceOver. |

## 9. Behavior changes on purpose

- No Inspector mode (owner, 2026-11-08; replaces Auto Inspector of 2026-11-07): the Inspector keys work whenever the VoiceOver cursor is on a track name in the Mix or Edit window, and act on that track. Off a track name, the key does what it does without the Inspector: another command for it runs, or the key goes to Pro Tools. Toggle Inspector (`/`), Toggle Temporary Inspector (backtick) and the preferences "Auto Inspector", "Use temporary inspector" and "Turn on the Flo Tools inspector when Pro Tools starts" are gone, and `/` and backtick go to Pro Tools. Each press of an Inspector key reads the VoiceOver cursor first, which delays it by that read.

- Tap and hold replace single and double press (owner, 2026-11-08): every command that had a single and a double action runs its single on a tap and its double on a hold. A tap runs as soon as the key is let go, instead of after the double-press timeout; a double press no longer runs the double action. The preference is the hold time (100 to 500 ms in 100 ms steps, default 200). It keeps the UserDefaults key of the former double-press timeout, so a saved value carries over as the hold time; the checkbox "Hold a key for a double press" is gone. KM had only double presses.

- VoiceOver communication (owner, 2026-11-07): use only the “Flo Tools started.” announcement as the startup check; remove the silent request on Pro Tools launch. A failed startup request says “Flo Tools could not communicate with VoiceOver. Allow VoiceOver to be controlled with AppleScript in VoiceOver Utility.” It does not claim the setting is off, since other failures look the same, but names the setting to check, as the KM alert did (owner, 2026-11-07). VoiceOver may speak even if its reply fails.

- Freeze wait and Cancel (owner, 2026-11-07): the wait after a hold of F has no time limit and runs as a watch, so other keys work meanwhile. Flo Tools now catches Cmd+. in Pro Tools, passes it on, and ends the freeze wait, because a cancelled freeze leaves the button name unchanged and the wait could not otherwise end. Holding F again cannot cancel: VoiceOver does not answer while Pro Tools renders, so the press cannot find the track.

- Speak Shown Frozen Tracks (Option+Shift+F) uses the Track List to identify shown tracks and the Edit track freeze buttons to read their state. A missing freeze control on a track that can freeze surfaces as a read failure. A tap announces the list. A hold presses the freeze buttons of shown frozen tracks, verifying each unfreeze before continuing. Hidden tracks are excluded.

The port kept every shortcut's behavior except these, which the keymap baselines show.

- Ctrl+Cmd+Left and Right switch track views whenever the VoiceOver cursor is not on a track name, and pan when it is; the KM version needed one `/` before they switched track views.
- AudioSuite keys work only in AudioSuite windows. KM's Audio Suite group took any title containing "Audio Suite:", so a plug-in window such as "Plug-in: Audio Suite: X", or a Mix or Edit window of a session with that in its name, also got the AudioSuite buttons and presets. Pinned in `Routing.txt`.
- A queued press of a command for some windows is dropped if another window comes to front before it runs, also one of the same kind and title, such as a second instance of one plug-in (Codex review, 2026-11-03). Plug-in and Inspector commands act on the front window, so they would otherwise act on a window the user did not press the key in. This includes a switch between Mix and Edit; any-window commands still run.
- The Inspector pan and volume keys (Ctrl+Cmd+arrows, Ctrl+Shift+Cmd+Left and Right, Ctrl+Opt+arrows) repeat while held, at the system key repeat delay and rate (owner's decision, 2026-11-03); in KM each press moved one step. Each step waits for the previous one to finish, and repeating stops on key release, when the key is no longer down, or when a step fails. `repeats while held` in `Keymap.txt`.
- New plug-in window keys Ctrl+Cmd+Up and Ctrl+Cmd+Down (owner's decision, 2026-11-03): step the current parameter of the loaded plug-in view through its Accessibility slider (AXIncrement, AXDecrement) and speak the new value; held, they repeat like the Inspector volume keys. They work only for parameters the plug-in shows as sliders. KM had no key that changed a parameter.
- Track View Toggled on All Tracks (Opt+-) sends Ctrl+Opt+- to Pro Tools, because Pro Tools 26.10 ignores the Opt+- the KM version sent (checked live 2026-11-03). The hotkey stays Opt+-.

- List Frozen Tracks (owner, 2026-11-18) is an option in List Tracks with Flo Tools (Ctrl+Opt+Shift+L). It lists the same shown frozen tracks as Option+Shift+F and offers Unfreeze for the chosen tracks, checking each result. Hidden tracks stay excluded; an empty list says “No shown tracks are frozen.” TrackQuery runs through ProToolsApp because its queries use both Mix and Edit.

- List DSP Tracks and List Auto-Enabled DSP Tracks (owner, 2026-11-18) are separate choices in Ctrl+Opt+Shift+L. Both use shown Mix track strips and the DSP button identifier dspm; exact labels distinguish Native, explicitly enabled DSP and routing-enabled automatic DSP, because AXValue is Selected for all three. The explicit DSP list offers Toggle DSP: a normal button press after rechecking each chosen track is still explicitly enabled, followed by state-change verification. Routing may leave a track in automatic DSP. The auto-enabled DSP list is read-only, explains the routing dependency, and offers Close. TrackQuery rejects changes through read-only DSP queries before reading Accessibility. Neither list changes DSP Safe, routing, record or input-monitor settings. Unknown DSP labels surface as read errors.

- Inspector D (owner, 2026-11-18): tap speaks “DSP”, “Native” or “Auto DSP” for the track under the VoiceOver cursor. Hold presses the DSP button in any of those states, including automatic DSP, leaving any Pro Tools routing warning open for the user. The command speaks the resulting state only when a Mix or Edit window remains in front. Off a track name or while typing, D goes to Pro Tools through normal Inspector routing. The automatic DSP chooser remains read-only.

- New Tracks announcements (owner, 2026-11-19): preserve the native Cmd+Left/Right format, Cmd+Up/Down type and Opt+Cmd+Up/Down timebase shortcuts and speak the resulting pop-up value. Cmd+Plus/Minus and Shift+Cmd+Up/Down announce the resulting number of track-entry rows. These commands run only in New Tracks; Cmd+Shift+N stays native. Read each row’s immediate pop-ups by Accessibility description and compare values before/after, identifying changed rows when there are several. At an unchanged boundary, speak all current row values rather than guessing the active row. Reuse the shared pass/wait/speak implementation with Equatable readings and the 500 ms passed-key limit. Row-count speech waits another 100 ms after the count changes because native focus speech otherwise followed and displaced it in a live deletion test. No control is focused or opened by Flo Tools.

- Selected-track movement (owner, 2026-11-19): Ctrl+Shift+Cmd+P moves selected tracks one position earlier (up in Edit, left in Mix); Ctrl+Shift+Cmd+semicolon moves them later. TrackList reads names/order/selection, removes positional labels only when View > Track Number is on, derives the expected permutation and verifies the whole order and selection after dragging. Track List frames ignore scroll offset, so movement uses the actual window track-name and neighboring strip frames instead. Before dragging, native Scroll Into View reveals the neighbor and source, waiting for each popup window to close (about 400 ms live); any selection changes from revealing are restored. FloSystem finds context menus by their own popup-window bounds and AX hit-testing at several points, validating the owner and avoiding VoiceOver caption-panel occlusion, because they are omitted from Pro Tools’ app tree. Popup reads retry only busy-app errors for at most one second because the window can appear before its AX objects answer. Mix drags horizontally; Edit drags vertically. The native gesture uses three motion events spaced 150 ms after matching move/down pauses: single-motion drags did not reorder tracks in live testing. Modifiers must be released first; each motion checks the front app/window and every pressed button is released on cancellation/failure. The implementation accepts a contiguous selection in a Track List without folders or duplicate names, and requires shown source/destination strips that fit on screen after revealing. It does not gather nonadjacent tracks or move hidden tracks. At a boundary it speaks without dragging. No session is saved by this command.

## 10. Not done on purpose

No KM action interpreter, no plugin system for commands, no protocols for mocking Accessibility or VoiceOver, no shell commands at runtime except the `tccutil` permission reset (section 8), no telemetry. No buffering of keys pressed before the window title is read (section 3). No caching of watch elements (section 3).
